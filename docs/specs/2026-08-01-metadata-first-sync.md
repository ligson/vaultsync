# 元数据优先同步设计

## 背景

原拉取流程收到每个远端 `upsert` 事件后都会下载完整对象，再解密并交给本地写入器判断是否存在冲突。对于当前设备刚上传的文件，客户端会再次下载自己上传的完整内容；相册和大文件较多时会浪费网络流量和等待时间。

本设计在下载前建立本地版本基线，并利用变更接口已经返回的小型元数据判断是否需要下载。服务端对象、SQLite 表和变更游标协议保持不变。

## 本地版本基线

文件上传成功并经服务端确认后，客户端立即保存以下信息：

- `sync_root_id`
- `object_id`
- `version_id`
- 本地相对路径和本地绝对路径
- 明文内容的 SHA-256

下载并成功写入本地文件时，继续沿用原有逻辑保存同类基线。基线只作为客户端判断依据，不上传本地绝对路径。

## 拉取决策顺序

客户端收到远端 `upsert` 后按以下顺序处理：

1. 本地基线中的 `version_id` 与远端一致时，说明远端版本没有变化，直接推进游标，不下载文件。
2. 同步目录使用“上传后删除本地”策略时，该目录按单向备份处理，不自动把远端文件下载回本地。
3. 如果 `object_id` 和 `version_id` 能匹配本机已完成的稳定上传任务，则判定为本机上传产生的变更，不下载文件，并在本地文件仍存在时补写版本基线。
4. 读取变更事件携带的元数据。若其中包含 `client_content_hash`，且本地对应文件的 SHA-256 与其一致，则补写版本基线并跳过下载。
5. 无法确认一致，或远端内容确实发生变化时，才下载完整对象，继续执行密文校验、解密、本地写入和冲突保护。

无论下载还是跳过，只有整页变更处理成功后才保存新的远端游标，避免异常中断时漏掉变更。

## 清理策略语义

### 保留本地文件

该策略用于双向同步。远端版本未变化时不会重复下载；本地内容变化由目录扫描生成新的上传任务。远端出现未见过的新版本时，客户端才下载并进入原有写入与冲突判断流程。

### 上传后删除本地

该策略用于单向备份。上传、服务端校验和本地清理完成后，远端文件继续保留，但客户端不会因为拉取到自己的上传事件而恢复已删除文件。用户仍可在服务器备份浏览界面主动预览或下载文件。

## 内容指纹与隐私

- 普通存储目录：`client_content_hash` 写入普通 metadata，便于客户端比较。
- 加密存储目录：`client_content_hash` 放在 XChaCha20-Poly1305 加密的 metadata 内，服务器只保存密文，无法直接读取明文文件哈希。
- 指纹只用于判断内容是否相同，不替代下载后的密文大小和 SHA-256 完整性校验。

## 兼容与数据安全

- 不新增或迁移后端 SQLite 字段，不调整服务端对象存储路径。
- 不清空客户端 `SharedPreferences`，不删除目录绑定、上传队列、同步历史、冲突记录、同步游标和加密密钥。
- 旧上传对象没有 `client_content_hash` 时，客户端不能仅凭指纹确认一致，会回退到原完整下载流程。
- 已存在的本地版本索引继续读取，新上传或确认一致的对象逐步补齐基线。
- 回滚到旧客户端时，新 metadata 字段会被忽略，服务端数据仍可正常使用。
