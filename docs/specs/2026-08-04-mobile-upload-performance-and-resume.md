# 移动端上传性能与断点恢复优化

## 1. 问题

Android 真机在扫描、上传或重试上传时出现界面卡顿和 ANR。系统记录显示 VaultSync 连续 5 秒无法处理输入，进程 CPU 占用约 80%，内存从约 224 MB 上升到约 690 MB。华为系统还曾以低内存原因回收处于前台服务状态的 VaultSync 进程。

当前上传链路会一次性读取完整文件，计算 SHA-256、生成完整密文，再按 1 MB 切片上传。大文件处理期间同时保留明文、密文和切片副本。上传进度保存和扫描入队还会在 Flutter UI isolate 上对完整任务列表执行 JSON 编解码。

## 2. 目标

- 大文件上传内存占用与文件大小解耦，避免因整文件常驻内存触发 ANR 或系统回收。
- 保持现有 `VSENC001` 密文格式、服务端上传协议和已上传对象完全兼容。
- App 被系统回收后，以服务端上传会话的 `received_size` 为准恢复真实进度。
- App 重新打开后自动恢复未完成上传，不要求用户再次点击“上传”。
- 保留现有 `SharedPreferences` 中的目录映射、上传队列、相册记录和加密密钥。

## 3. 方案

### 3.1 流式上传内容

- 普通文件使用文件流计算 SHA-256，并按网络分片读取，不再调用 `readAsBytes()`。
- 加密文件继续使用 `XChaCha20-Poly1305` 和 `VSENC001`：先写固定头和 nonce，再使用 `Cipher.encryptStream()` 把密文流写入 App 临时目录，最后追加 MAC。
- 临时密文使用任务版本派生的稳定文件名，并通过 `.part` 写入后原子重命名。只有完整文件和 sidecar 元数据都存在且大小、源文件大小和修改时间一致时才允许复用。
- 上传成功后删除对应临时密文；失败或进程退出时保留，用于下次继续上传。过期缓存可在后续版本按明确规则清理，不影响服务器对象。

### 3.2 服务端进度优先

- 已有 `upload_session_id` 的任务在准备内容前查询服务端会话，并立即展示 `received_size / total_size`。
- App 启动时校准最近的未完成会话，把服务端进度写回原任务记录。
- 网络上传从服务端 `received_size` 对应偏移继续读取临时密文，不重新发送已确认分片。
- 本地进度只作为离线展示和性能优化；服务端会话始终是断点恢复的最终事实来源。

### 3.3 扫描与任务存储

- 上传任务 JSON 编解码移到后台 isolate，继续使用原有 key 和 JSON 字段，旧队列无需迁移。
- 进度持久化间隔从 8 MB 调整为 32 MB；会话创建后仍立即保存。进程异常退出后由服务端进度校准补齐最多 32 MB 的本地显示差异。
- 扫描和任务合并按固定批次主动让出事件循环，避免大量文件排序、合并时长时间阻塞界面。

### 3.4 后台行为

Android 前台服务继续用于提高进程优先级。它不承载另一套上传协议；内存降低后，系统因低内存回收进程的概率显著降低。如果系统仍回收进程，App 下次启动会自动校准并恢复待上传任务。

## 4. 数据影响与兼容

- 不修改后端数据库、对象路径、上传接口或分片协议。
- 不重写、不迁移已上传的 `VSENC001` 密文对象。
- 不清空或替换客户端 `SharedPreferences`、同步目录绑定、上传队列、相册记录、同步历史或加密密钥。
- 新增临时密文仅位于 App 临时目录，不是唯一数据副本；源文件和服务器已确认分片仍按原规则保留。
- 回滚旧 App 时，新增临时文件会被忽略；原上传任务 JSON 保持兼容，旧 App 仍可按原方式重建密文并续传。

## 5. 验收

- 大文件准备和上传期间界面持续响应触摸，不再出现 5 秒输入超时。
- 上传内存不再随文件大小按多份副本增长。
- 上传部分分片后终止进程，重新打开 App 能显示服务端真实进度并从该偏移继续。
- 旧密文仍可预览、下载和解密；新上传密文可由现有下载解密器读取。
- 原有上传队列、目录绑定、相册记录和密钥在覆盖升级后保持不变。
