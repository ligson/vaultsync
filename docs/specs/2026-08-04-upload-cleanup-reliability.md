# 上传后本地清理可靠性

## 背景

旧客户端将上传任务整体保存在 `SharedPreferences`。macOS 的
`NSUserDefaults` 单项数据约 4 MB 后无法可靠写入，大目录可能出现内存状态与磁盘状态不一致。
同时，本地清理只在整轮上传结束后执行，且不会重新处理使用“保留本地文件”策略完成的
`clean` 任务。

## 行为

- 每个文件完成服务端确认后，先持久化 `uploaded`，再执行当前目录的本地清理策略，最后持久化
  `clean`、`deleted_local`、`archived` 或 `cleanup_pending`。
- “上传后删除”仅删除大小和修改时间仍与上传任务一致的普通文件。内容发生变化时进入
  `cleanup_pending`，不强制删除。
- 已不存在但服务器上传已完成的普通文件记录为 `deleted_local`，避免永久重试清理。
- 目录从“保留本地文件”切换为“上传后删除”时，界面提示已备份旧文件数量并要求确认。
  升级前已经切换过策略的 `clean` 任务也显示为待清理，可从同步状态重新执行。
- 相册资源继续使用系统相册删除能力，并保留逐项确认流程。

## 跨平台任务存储

上传队列迁移到应用支持目录下的 `vaultsync/upload-tasks-v1/`：

- 任务按稳定 ID 哈希分为 32 个 JSON 分片，单任务进度更新只读写一个分片。
- JSON 编解码使用后台 isolate；批量保存只替换内容变化的分片。
- 分片和清单使用同目录临时文件与备份文件原子替换，启动时可恢复中断的写入。
- 方案只依赖 Dart 文件 API 和 `path_provider`，适用于 Android、iOS、macOS、Windows 和
  Linux，不引入平台专属 SQLite 驱动。

## 迁移和数据影响

首次读取新存储时会合并旧 `vaultsync.upload_tasks` 和任何可恢复的新分片，以任务 ID 去重，
新分片优先。只有全部分片写入成功后才创建版本清单。旧 `SharedPreferences` 键保留为迁移备份，
升级不会清空上传任务、目录绑定、相册记录、同步历史或加密密钥。

如果旧平台此前已经因为系统大小限制而拒绝写入，进程退出前未落盘的内存任务无法由升级包恢复；
后续扫描会依据本地文件和服务器状态重新建立任务，不删除服务器版本。

## 回滚

代码回滚不会修改或删除 `upload-tasks-v1/`。旧版本仍会读取保留的
`SharedPreferences` 快照，但看不到升级后新增的分片进度，不建议在仍有上传任务时回滚。
如必须回滚，应先备份整个应用支持目录；恢复新版本后会继续读取分片状态。
